# Establish the chat's worktree before writing

1. Inspect the active chat's actual workspace/host association, repository root, branch, HEAD, existing worktrees, and working changes using supported app tools and read-only Git commands. Record the task's intended starting commit and any explicitly requested uncommitted input. Use the user's selected base; otherwise use the starting HEAD of the selected project/chat. Preserve unrelated changes. Do not stash, reset, commit, or transfer unrelated dirty files to make setup convenient. If dirty work cannot be separated safely, stop before moving or writing.
2. Prefer the app's managed Worktree mode or Handoff for this same chat. If it already has a newly provisioned dedicated worktree for this task, retain it. Otherwise obtain a fresh worktree associated with this chat through a supported capability. Native controls may reuse a chat's previously associated worktree: verify that it belongs to this task before accepting it. Do not create a second chat, fork, or helper chat merely to work around an attachment limitation. Starting a separate task requires an explicit user request.
3. Check the running tool schema. In the currently inspected app interface, `handoff_thread` cannot move its calling thread; do not call it on yourself or manipulate app databases/configuration to bypass that restriction. A supported current-chat UI control may be used when available and authorized. If the current chat cannot be moved through available controls, stop before implementation and give the user the exact native action: Hand off this chat to Worktree. If the chat has no usable repository/worktree association, ask the user to select the repository in Worktree mode. Explain the actual capability limit rather than claiming shell commands changed the chat. Non-Git folders block this implementation workflow; do not initialize a repository or create an initial commit automatically.
4. Inside the verified worktree, create and check out a new, unused branch with a neutral task name such as `feat/<task-slug>` or `fix/<task-slug>`, unless the host already created a new branch for this task. Use the user's exact requested new name when provided; do not overwrite an existing branch on a collision. Branch creation requires no commit. Preserve the recorded base and distinguish existing user changes from this task. Resume on this same branch throughout repairs and later turns.
5. Verify BOTH layers before edits: the app-reported chat workspace is the task worktree; `git rev-parse --show-toplevel`, `git branch --show-current`, and `git worktree list --porcelain` agree on its absolute path and new branch. Record the chat ID when exposed, worktree path, branch, and base in existing task evidence. If host association cannot be verified, report it as blocked rather than substituting a shell working directory. Check again after any handoff, resume, or unexpected cwd/branch change. Subagents use this exact root for commands and edits; they do not create additional worktrees or branches.

Only this task's worktree is used for implementation and shown in its file/review panels. This does not remove other chats/worktrees from the global sidebar, erase prior conversation references, or change filesystem permissions. Required installed skills/tools and task evidence can remain outside the source root. Do not claim a hard filesystem sandbox.

Official app behavior checked 2026-09-10: [Worktrees](https://learn.chatgpt.com/docs/environments/git-worktrees). Worktree chats may start detached, and Handoff manages chat/worktree association. Actual callable tools determine whether the current chat can perform the move itself.
