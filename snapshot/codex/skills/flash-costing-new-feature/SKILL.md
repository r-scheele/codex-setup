# Flash Costing Feature Implementation

Read `flash-costing-guidelines` once for shared domain, workspace, authorization, and verification policy. Use the active checkout’s applicable AGENTS.md and only relevant domain references. If the companion skill is unavailable, continue from the checkout’s instructions and report a missing rule only if it prevents a safe decision.

1. Establish the requested behavior and acceptance criteria from the current request and accessible linked/attached evidence. Reuse behavior already present in the active code.
2. Identify affected roles, state/persistence, API paths, and UI surfaces. Resolve only material product or permission ambiguity; do not require a separate design approval when the task is already clear.
3. Implement the complete requested outcome using existing patterns. Preserve capabilities and non-target behavior unless their removal is explicitly required.
4. Exercise relevant acceptance criteria and regression boundaries using the shared project policy; continue until the authorized outcome is verified or a concrete blocker remains.

If evidence conflicts on a material product decision, explain the conflict and ask only about that decision while continuing independent investigation. Missing prose pasted into chat is not a blocker when the request is available elsewhere.

For UI work, inspect a comparable current screen and preserve its components, accessibility, saved state, and design system. Use actual product/browser proof for visible claims.

Handoff: state the outcome, why it changed, relevant verification, and concrete limitations. Include technical paths or screenshots when they help review the change. Do not pad the response with a fixed report template.
